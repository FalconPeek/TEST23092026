# T-014 worker report

## Summary
Built the match-detail hub page: header (teams/date/venue/status/deadlines), lineups with
profile links, and — gated on eligibility and window — the score form, per-team stats form,
and match-rating form, all against the T-010 `lib/actions/matches.ts` functions. Payload
building and the two live checks live in a new pure `lib/match/report.ts`.

## Files changed
- `messages/es.ts` — added a **new** top-level `match.*` (singular; distinct from the
  existing plural `matches.*` from T-010/T-013, per the task's explicit key) with every
  string listed, plus a few the task described narratively without a literal string, which
  I wrote reasonably: `reportDeadlineHint`/`ratingDeadlineHint` as functions over
  `formatDate` (matching the "…antes del {date}" phrasing given), `goals`/`assists`/
  `ownGoals`/`saves` short labels for the stats-form column headers, `showSaves` (the
  "mostrar atajadas" toggle label), and `goalsLoaded(loaded, expected)` for the live check
  text.
- `lib/match/report.ts` (new) — pure, no I/O. `buildStatReportsPayload` keeps a row only if
  it has a non-zero value **or** `wasPreviouslyReported` (so an edit can clear a stat back
  to zero — a row with all-zero values that was never reported before is just noise and
  stays unsent). `goalsCheck(stats, score, side)` — matched the task's literal 3-arg
  signature rather than inventing my own shape — sums one side's currently-entered goals and
  compares to that side's reported score; it's informational only, both callers (component
  and page) treat a mismatch as a warning, never a block. `ratingsComplete` requires every
  id in `requiredPlayerIds` to have a defined rating (and is `false` for an empty required
  list — "nothing to rate" isn't "complete", it's a state the page should never actually
  reach since the form isn't rendered without teammates).
- `lib/match/report.test.ts` (new) — 10 tests: the zero-vs-previously-reported filter, the
  camelCase→payload field mapping, `goalsCheck` per-side summing and the null-score/no-report
  case, `ratingsComplete`'s partial/complete/empty cases, `buildRatingsPayload`'s
  undefined-rating filter.
- `components/match/score-form.tsx` (new) — two 0-99 steppers (±1, `size-11` = 44px buttons,
  meeting the tap-target requirement) prefilled from my existing report if any.
- `components/match/stats-form.tsx` (new) — rows grouped by side, each with 3 compact
  steppers (goals/assists/own goals, max 30 matching the RPC's own range) plus a 4th
  (saves, max 99) shown only when that row's player is `POR` or the "mostrar atajadas"
  toggle is on. Per-side header shows `goalsLoaded` only once I have a score report for that
  side (`expected !== null`) — before that there's nothing meaningful to compare against.
- `components/match/rating-form.tsx` (new) — one card per (non-self) team player: a 1-10
  grid of `h-11` buttons, then a standout-attribute picker. Implemented "searchable list"
  literally (a text filter over `es.attributes`, matches shown as toggleable chips below,
  max 2 — the 5th already-picked one shows as a removable chip above the search box) rather
  than a flat always-visible chip list, since a GK's pool is 34 attributes and this control
  repeats once per teammate on the page — a flat list at that multiplicity would make the
  page unusably long. Submit is disabled until `ratingsComplete` is true for every player in
  the `players` prop.
- `components/match/rating-form.test.tsx` (new) — submit stays disabled until every listed
  player is rated then enables; the exact `submitMatchRatings` payload once complete; the
  max-2-standout cap (3rd pick disabled, 2 chips shown); prefill of a previous rating +
  standout. "Self excluded" is exercised by construction: the `players` prop passed to every
  test never includes a "self" entry, which is exactly the contract the page relies on (the
  page never puts the rater in that list) — the component itself has no self-filtering logic
  to test, since it's never handed a self entry in the first place.
- `app/g/[groupId]/partidos/[matchId]/page.tsx` (new) — loads the match (404 if wrong group
  or not visible), teams, participants embedded with their `players` row, my role, and
  group settings, in parallel; then — only if I have a player row in this group — my own
  score/stat/rating rows (RLS already restricts these to my own anyway, but the query still
  filters explicitly by `reporter_player_id`/`rater_player_id` for clarity of intent) and
  `get_match_report_summary`, also in parallel. Renders the score/stats forms only when
  `status === "reporting"`, I'm a **team player** participant, and `now <
  report_deadline`; the rating form when status is `reporting` **or** `pending_finalize`,
  I'm eligible (team player, or a match-level spectator when the group's
  `spectators_can_rate` allows it), and `now < rating_deadline` — matching the task's two
  independent windows exactly. `finalized`/`disputed`/`cancelled` currently just show the
  status badge with no forms (T-015 owns those sections per the task's own note). Hit one
  new-to-this-codebase lint error here: `eslint-config-next`'s `react-hooks/purity` rule
  flags the bare `Date.now()` call used for the two deadline checks, even inside a Server
  Component (which genuinely does need "now" once per request — this isn't the double-render
  purity concern the rule exists for). No other file in the codebase had hit this rule
  before (checked — every other `Date.now()`/`new Date()` call is in `lib/server/*` or a
  route handler, never a page body), so there was no established pattern to follow; added a
  single scoped `eslint-disable-next-line react-hooks/purity` with a comment explaining why,
  rather than restructuring the deadline logic to dodge it or touching the shared eslint
  config.

score/stat/rating reads to my own rows**, so the page's prefill logic (query only
