# T-013 worker report

## Summary
Built the matches list (upcoming/recent), the "new match" form, and the lineup editor with
tap-to-cycle assignment, auto-balance (via `lib/rating/balance.ts`), team name/color
editing, and the terminate/cancel actions — all against the T-010 `lib/actions/matches.ts`
functions. State transitions live in a new pure `lib/match/lineup.ts`.

## Files changed
- `lib/format.ts` — added `toArgentinaIso(localValue)`: interprets a
  `<input type="datetime-local">` value as Argentina wall-clock time (hardcoded `-03:00`,
  correct since Argentina abolished DST in 2009 — no IANA lookup needed) and returns the
  UTC ISO string `createMatch` expects. Accepts both `HH:mm` and `HH:mm:ss` input shapes;
  throws `RangeError` on anything else, matching the existing `formatDate` etc. convention
  in this file.
- `lib/format.test.ts` — 4 new tests for `toArgentinaIso` (the UTC-3 conversion, the
  with-seconds variant, a round-trip through `formatTime`, and the `RangeError` case).
- `messages/es.ts` — extended the existing `matches` object (T-010 already put toast
  strings there) with every key the task listed, plus a `status.*` sub-object for the 6
  `match_status` enum values. `strength(mu, ovr)` and `cancelConfirm` had no literal string
  given in the task, so I wrote reasonable ones (`"μ {mu} · OVR {ovr}"`,
  "Esta acción no se puede deshacer." — reused for both the cancel and start-reporting
  confirm dialogs, since the task named only one `cancelConfirm` key and both actions are
  irreversible in the same way).
- `lib/match/lineup.ts` (new) — `Assignment = "unassigned" | "team1" | "team2" |
  "spectator"`. `nextAssignment` implements the 4-state tap cycle for a regular player,
  collapsing to a 2-state `unassigned <-> spectator` cycle for `isSpectatorRole` players (a
  member who was demoted to the `spectator` group role but still has a `players` row from
  before the demotion — confirmed this is a real, reachable case against the live DB, not a
  hypothetical, see Manual verification). `cyclePlayer`/`applyBalance` are generic over
  `T extends LineupPlayer` (not hardcoded to the base type) specifically so
  `lineup-editor.tsx` can pass its own `EditorPlayer` (which adds `displayName`/`avatarUrl`)
  through them without a cast losing those fields — the alternative (casting the return
  value back to `EditorPlayer[]`) would silently compile even if a future refactor broke the
  field-preservation invariant; the generic makes the compiler enforce it structurally.
  `applyBalance` only touches players not already marked `spectator` (the "selected"
  players per the task), leaving spectators and their `position` field untouched, and calls
  `balanceTeams` from `lib/rating/balance.ts` exactly as specified.
- `lib/match/lineup.test.ts` (new) — the cycle order for both player kinds; that a
  spectator-role player's cycle never lands on `team1`/`team2` even starting from one (a
  defensive case: shouldn't happen via the UI, but the function itself must never produce an
  invalid state regardless of input); `position` surviving a cycle and a balance;
  `applyBalance` splitting only non-spectator players 2/2 with spectators untouched;
  determinism for a fixed seed; `countByAssignment`/`teamStrength` including the empty-team
  zero case.
- `app/g/[groupId]/partidos/page.tsx` — replaced the T-006 "coming soon" placeholder.
  Fetches `scheduled` matches (ascending) and everything else (descending, `limit(30)`) as
  two separate queries rather than one big query + client-side split, so the 30-row cap is
  enforced by Postgres, not by discarding already-fetched rows. Each card embeds
  `match_teams`/`match_results` via PostgREST (`match_results` is `isOneToOne`, so it comes
  back as a single object or `null`) and shows the score only when a result exists, "vs."
  otherwise. "Nuevo partido" only renders for admins (checked via `group_members.role` +
  `isGroupAdmin` from `lib/permissions.ts`, T-008).
- `app/g/[groupId]/partidos/nuevo/page.tsx` (new) — admin-only (`notFound()` otherwise, no
  UI hint that the page exists to a non-admin, matching the acceptance criteria), loads
  `groups.settings` and parses it with `parseGroupSettings` to seed the team-size select
  with the group's real `default_team_size` rather than a hardcoded `5`.
- `components/match/create-match-form.tsx` (new) — datetime-local + venue + team-size
  select (5/6/7/8/9/11). Converts via `toArgentinaIso` right before calling `createMatch`;
  on success, navigates straight to that match's `/equipos` lineup editor (per the task's
  step 2 "On success →").
- `components/match/create-match-form.test.tsx` (new) — blocks submit with no date/time;
  the Argentina-time conversion + exact `createMatch` args + navigation on success; the
  mapped-error-without-navigating path; the team-size select's default.
- `components/match/lineup-editor.tsx` (new) — four sections (Team 1, Team 2, Espectadores,
  Sin asignar) driven entirely by each player's `assignment`, so a player only ever appears
  in one section at a time — tapping a row calls `cyclePlayer` and the re-render moves it.
  Per-team name/color inputs, a live `teamStrength` summary, and a `count/teamSize` badge
  that turns `destructive` on mismatch (not a hard block — "Armar parejos" and "Guardar
  equipos" both still work with an uneven roster, matching "balance is only a suggestion").
  The balance button reads "Armar parejos" until any player has landed on a team, then
  "Rearmar" — matches the task having both strings as distinct, purposeful labels rather
  than one being dead copy. `handleSaveLineup` blocks (client-side, before calling the
  action) when either team has 0 players — `setMatchLineup`'s own zod schema in
  `lib/actions/matches.ts` (from T-010) requires `players.min(1)` on **both** teams, a
  stricter check than the SQL's own "at least one player across the whole lineup"; I didn't
  relitigate that T-010 decision, just made sure the editor can't produce a request the
  action would reject anyway. "Terminó el partido" and "Cancelar partido" both go through a
  confirm `Dialog` before calling `startReporting`/`cancelMatch`.
- `app/g/[groupId]/partidos/[matchId]/equipos/page.tsx` (new) — admin-only, and additionally
  `notFound()`s when the match isn't `status: "scheduled"` (editing a lineup mid-report
  makes no sense and the RPC would reject it anyway). Builds each player's
  `isSpectatorRole` from a **separate** `group_members` query cross-referenced by
  `user_id` (not from the `players` row itself, which has no role column) — confirmed this
  is exactly right against a real demoted member in the Manual verification below.
  `mu`/`ovr` default to `25`/`60` per the task when a player has no `openskill_ratings` /
  `player_cards` row yet (the common case for a freshly-created group).

## Manual verification
Chrome extension still not connecting (same as every prior task). Ran the real RPC sequence
against the live stack with 6 real users (owner + 4 members + 1 more), specifically to
exercise the one rule in this task that's easy to get wrong on paper: **a spectator-role
member can still have a `players` row** (from before they were demoted) and the lineup
editor must never let them onto a team.
- Created a group, added 4 members, then demoted the 5th to `spectator` via
  `set_member_role` — confirmed their `players` row survives the demotion (matches T-008's
  `remove_member`/`set_member_role` behavior: role changes never touch `players`).
- Ran the exact two queries `equipos/page.tsx` runs (`players` where `group_id`/`left_at is
  null`, and `group_members` for the role cross-reference) and confirmed the demoted
  member's `user_id` lands in the `spectatorUserIds` set my page builds — i.e. their
  `isSpectatorRole` flag would be `true` in the real editor, not just in a hand-built test
  fixture.
- Called `set_match_lineup` with a valid 3v3 lineup (3 real players per side, one spectator)
  — succeeded, and read `match_teams`/`match_participants` back to confirm the prefill
  mapping in `equipos/page.tsx` (team_id → side → assignment, `role: 'spectator'` → no
  `team_id`, `position` preserved per player) matches real data exactly.
- Then called `set_match_lineup` again on the same match, this time putting the
  **demoted/spectator-role player on team 1** — rejected by the real SQL with
  `PICADO_VALIDATION: a spectator-role member cannot be a team player`, confirming the
  editor's `isSpectatorRole` restriction exists to prevent an action that would genuinely
  fail server-side, not a hypothetical.
- Confirmed brand-new players have zero `openskill_ratings` rows, exercising the page's
  `mu ?? 25` default path with real (absent) data.
- `create_match` and `cancel_match` both round-tripped cleanly.
- Did not click through the rendered pages in a browser, for the same environment reason as
  every prior task; the RPC-level walkthrough above exercises the exact calls
