# T-025 worker report

## Summary
- `messages/es.ts`: added `dashboard.*` — `title`, `pickGroup`, `noGroups`, `ovrHistory`,
  `recentMatches`, `totals`, `impacto`, `noHistory`, `result.{win,draw,loss}`. Also added
  `dashboard.noMatches` ("Todavía no jugaste ningún partido."), a small necessary string the
  task's list didn't name but the "recent matches" section needs for a brand-new player with zero
  matches yet.
- `lib/dashboard/schema.ts` (+ test): a zod schema for `get_my_dashboard`'s hand-built jsonb
  result (read `supabase/migrations/20260923211743_dashboard_rpcs.sql` for the exact shape, not
  guessed). Chose `.catch(<empty default>)` over `.default()` for every collection/scalar field
  (documented in the file's own comment) specifically because `.catch()` also recovers from a
  field being *present but the wrong type*, not just a missing key — matching the RPC's own
  "every field defaults to empty rather than omitting the key" contract on the client side too.
  `player_id` is the one field with no fallback: if it's missing or not a valid uuid, the whole
  response is unusable, so `parseDashboard` returns `null` rather than fabricate a fake id. The
  `card` field is validated only as "an object or null" (`z.unknown().nullable().catch(null)`) —
  `lib/cards/to-card-props.ts`'s `toCardProps` already does its own defensive per-field parsing
  and returns `null` on any mismatch, so re-validating the full `player_cards` shape here would
  just duplicate that. Tests: full valid payload, missing/invalid `player_id` → `null`, every
  collection defaults to `[]` when absent, `totals` defaults to an all-zero object when malformed,
  `impacto` defaults to `null` when the wrong type, and a completely non-object payload never
  throws.
- `components/charts/ovr-history-chart.tsx` (+ test): `'use client'` Recharts `LineChart` in the
  existing `ChartContainer` wrapper (same pattern as T-011's `FaceStatsRadar`), dates via
  `lib/format.ts`'s `formatDate`. Shows `dashboard.noHistory` for 0 *or* 1 points — a single
  snapshot has nothing to draw a line to. Tests: empty state at 0 points, empty state at 1 point,
  chart (not empty state) renders at 2+ points.
- `app/yo/page.tsx` (new): `getUserId()` redirects to login defensively (matching `/g/page.tsx`'s
  own belt-and-suspenders pattern even though `proxy.ts` already blocks anonymous requests to
  every non-public path, `/yo` included). Lists my groups via `group_members` joined with
  `groups(id, name)` (same query shape as `/g/page.tsx`); `?group=` is looked up against that list
  and only used if it matches one of mine, else falls back to the first — so a group id I'm not a
  member of can never reach `get_my_dashboard` (whose own `PICADO_NOT_MEMBER` check is the second
  line of defense if that fallback logic were ever wrong). A horizontally-scrollable group switcher
  (chip links, ≥44px) shows only when I'm in more than one group. Renders, in order: the card
  (`size="md"`) with Impacto underneath, `OvrHistoryChart`, a totals tile grid (matches, goals,
  assists, MVPs, clean sheets, saves), recent matches, and `BadgeList`.
  - **Recent matches needed two extra queries beyond the RPC.** `get_my_dashboard`'s
    `recent_matches` items (verified against the migration) carry per-player stats
    (`goals`/`assists`/`saves`/`clean_sheet`/`is_mvp`/`median_rating`) but **no team score or
    win/draw/loss outcome** — the task's step 3 asks for "score" and a "W/D/L chip" that the RPC
    simply doesn't provide. I fetch `match_results` (score + `winner_side`) and
    `match_participants` joined with `match_teams(side)` (which side I played on) for the ≤10
    match ids, and derive the outcome myself (`draw` when `winner_side` is null, else `win`/`loss`
    by comparing to my side). Flagging this in case the RPC should be extended instead — for now,
    two small extra queries, matches-id-count bounded at 10, is a reasonable client-side fill-in.
  - `BadgeList` needs each badge's `icon` string, which `get_my_dashboard`'s `badges` array also
    doesn't return (only `badge_code`/`awarded_at`/`count`); fetched the whole (15-row) `badges`
    catalog once and joined by code.
  - The player's `avatar_url`/`preferred_foot`/`display_name` (needed by `toCardProps`, not part
    of the RPC's `card` field which is `player_cards` minus `player_id`) come from a plain
    `players` lookup by the RPC's own returned `player_id`.
