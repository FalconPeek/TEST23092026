- `lib/actions/scouting.ts` (new) — `submitScoutingVotes`, `submitPlaystyleVotes`,
  `submitStarVotes`. Votes are validated with `z.partialRecord(z.enum(...), voteValue)`, not
  `z.record(...)` — **this mattered**: in zod 4, `z.record(enumKeySchema, valueSchema)` builds
  an *exhaustive* record requiring every enum member as a key, so `z.record(z.enum(OUTFIELD_FACE_STATS), ...)`
  would have rejected every real quick-mode vote (which only ever sends a subset of `pac/sho/pas/dri/def/phy`).
  Caught this because the first test run failed all 5 non-trivial cases with a validation
  error even on obviously-valid input; `z.partialRecord` is zod 4's purpose-built API for a
  partial map over a finite key domain. After a successful vote, calls
  `recomputeNow([targetPlayerId])` inside try/catch (comment explains the DB-trigger fallback
  per the task); still returns `ok` if it throws.
- `lib/actions/matches.ts` (new) — `createMatch`, `setMatchLineup`, `startReporting`,
  `cancelMatch`, `submitScoreReport`, `submitStatReports`, `submitMatchRatings`,
  `resolveDispute`. `teamSize` is restricted to `{5,6,7,8,9,11}` per the task's zod spec even
  though `create_match`'s own SQL check is looser (`between 3 and 11`) — the task's list is
  the canonical set of sizes the rest of the app supports (`default_team_size` in
  `lib/settings/group.ts`), so the client-side schema is intentionally the stricter of the
  two. `setMatchLineup`'s cross-field refine collects every `player_id` across both teams'
  `players` and `spectators` and checks uniqueness client-side, mirroring
  `set_match_lineup`'s own `array_length(...) <> count(distinct ...)` check. `resolveDispute`'s
  optional per-stat fields (`goals`/`assists`/`ownGoals`/`saves`) are passed straight through
  as `undefined` when unset rather than `null` or `0` — `JSON.stringify` (which supabase-js
  uses for the RPC body) drops `undefined` keys entirely, which is what makes the SQL's
  `if (v_elem ? 'goals') then ...` *presence* check (as opposed to a null check) behave
  correctly: an unset field must be genuinely absent from the JSON, not present-with-null.
- `lib/actions/scouting.test.ts`, `lib/actions/matches.test.ts` (new) — 15 + 22 tests. Every
  function covers: invalid input never reaching `rpc`, the exact `p_*` args (including the
  snake_case JSON shapes: `player_id`, `subject_player_id`, `own_goals`, `target_player_id`,

  only after a **successful** vote (not after a mapped RPC error); and a `recomputeNow`
  rejection still yields `{ ok: true }`.

## Manual verification
No UI to click through — this task is pure Server Actions. Instead I read every relevant
migration in full rather than relying only on the task's Context/RPC-shape summary, and
found one real discrepancy worth flagging:
- `set_match_lineup`'s actual SQL additionally rejects a spectator-role group member being
  placed on a team as a player (`PICADO_VALIDATION: a spectator-role member cannot be a
  team player`) — not mentioned in the task text. This is a DB-side check that needs the
  member's `group_members.role`, which the action doesn't have in hand at validation time
  (it only receives player ids), so it's correctly left to the RPC to enforce; the action's
  job here is just to shape and forward the payload, which it does.
- `submit_scouting_votes` GK-attribute gating (`gk_*` keys only valid when the target's
  position is POR) is also target-dependent and correctly left to the RPC — the action's
  zod schema validates against the full `ALL_ATTRIBUTES` set for detailed mode, per the
  task's explicit instruction.
- Cross-checked every `PICADO_*` message text used in `errors.test.ts` and the action tests
  against the literal `raise exception '...'` strings in the migrations (not paraphrased),
  so `mapDbError`'s `startsWith()` prefix matching is exercised against real messages.
