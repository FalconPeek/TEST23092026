# T-012 worker report

## Summary
Built the scouting vote page: a quick/detailed tabbed slider form (with collapsible
attribute groups + a sticky save button above the bottom nav), a separate playstyles chip
picker (max 5, GK-only codes filtered for outfield targets), and two independent star
pickers — each with its own save action against the T-010 `lib/actions/scouting.ts`
functions. Disabled state shows the SQL-driven reason from `get_scouting_status`.

## Files changed
- `messages/es.ts` — added `scouting.*` (title/quick/detailed/help texts/scale/reasons —
  every key the task listed) plus one import (`formatDate` from `lib/format.ts`, needed for
  `reasons.cooldown`, per the task's explicit instruction to use it) and one small addition
  the task's message list didn't include but the slider component needs to keep all copy
  sourced from `es.ts`: `scouting.unset` = "Sin votar" (the untouched-slider label).
- `components/scouting/vote-slider.tsx` (new) — controlled: `value: number | undefined`
  (undefined = untouched, parent-owned), `onChange`. The Radix `Slider` always needs a real
  numeric thumb position even when untouched, so it renders at a neutral `5` until the first
  `onChange` fires (which is what actually marks it "touched" from the parent's point of
  view) — the displayed label switches from "Sin votar" to the number at that same moment.
- `components/scouting/vote-slider.test.tsx` (new) — unset label, numeric label once set,
  `onChange` fires on keyboard interaction, disabled state. Needed a local jsdom
  `ResizeObserver` polyfill (Radix `Slider` measures its track with one; jsdom has none) —
  added in this test file only, not the shared `vitest.setup.ts` (not in this task's Files
  list; same call I made for `hasPointerCapture` on Radix `Select` in T-009, flagging again
  that a shared polyfill for both would save re-adding these per test file next time
  something uses Radix `Select` or `Slider`).
- `components/scouting/scouting-form.tsx` (new) — quick tab: all 6
  `OUTFIELD_FACE_STATS` sliders, always initialized to a real value (default `5`, or the
  prefilled ballot value), so quick-mode submission always sends all 6 keys regardless of
  whether the user touched them — matches `submitScoutingVotes`'s `mode: "quick"` contract.
  Detailed tab: sliders start with **no** value (`{}` unless prefilled) grouped under
  `<details>` sections per `subAttributesOfFaceStat` (6 groups) plus a 7th "Arquero" group
  (`GK_ATTRIBUTES`) only when `isGk`; only keys present in the `detailedVotes` state object
  are sent, so an untouched slider is never submitted. The submit button is disabled when
  detailed mode has zero touched keys (nothing to send). Playstyle chips: `PLAYSTYLES`
  filtered to exclude `GK_PLAYSTYLES` for non-GK targets, capped at 5 via the same
  toggle-with-cap pattern used for alternate positions in T-009's player-profile-form. Star
  pickers: two independent 1-5 button rows (reusing `es.card.weakFoot`/`skillMoves` labels
  already defined for the card itself), each starts untouched; the stars save button is
  disabled until at least one is touched (mirrors `submitStarVotes`'s "at least one of
  weakFoot/skillMoves" requirement, so the user can never trigger the validation error from
  the UI). `!canVote` renders a destructive `Alert` with the reason text — for `"cooldown"`
  specifically, formats `nextVoteAt` via `es.scouting.reasons.cooldown(date)`; computed this
  as a typed `reasonText: string` local **before** the JSX rather than inline, because TS
  couldn't narrow `es.scouting.reasons[reason]`'s type away from the `cooldown` function
  signature inside a compound `reason === "cooldown" && nextVoteAt ? … : …` ternary (the
  `&&` means the false branch doesn't guarantee `reason !== "cooldown"`) — the fix is also a
  correctness improvement: the old shape would have rendered a raw function as `ReactNode`
  if `reason` were ever `"cooldown"` with a null `nextVoteAt`. The two secondary save
  buttons (playstyles, stars) use `es.common.save` ("Guardar") rather than
  `es.scouting.save` ("Guardar voto") — the task only specifies one `save` string for the
  whole form, but reusing it on all three buttons makes them ambiguous to both users and
  tests, so the primary vote button kept the more specific label and the other two fell
  back to the existing generic one instead of inventing new copy.
- `components/scouting/scouting-form.test.tsx` (new) — quick mode sends all 6 keys
  untouched; detailed mode sends only the one key actually dragged (located via its label
  text, then `within()` its wrapper to grab that specific slider — there are 29-34 sliders
  on screen in detailed mode, so this is the only reliable way to target one); GK
  attributes/playstyles hidden for a non-GK target and shown for a GK one; the 5-playstyle
  cap; the disabled-with-reason state; and the formatted cooldown date. Same
  `ResizeObserver` polyfill as `vote-slider.test.tsx`.
- `app/g/[groupId]/jugadores/[playerId]/votar/page.tsx` (new) — loads the player (404 if
  wrong group), calls `get_scouting_status` and `get_my_scouting_ballot` in parallel. Splits
  the ballot into `prefillQuickVotes`/`prefillDetailedVotes` **by each row's own `mode`**
  rather than treating the whole ballot as one mode — a target can in principle have both
  quick-mode rows (face-stat keys) and detailed-mode rows (sub-attribute keys) at once,
  since they're disjoint key namespaces and `submit_scouting_votes` only supersedes the
  attributes actually submitted each time, not the whole ballot. `initialTab` is the mode of
  whichever ballot row has the latest `created_at` (falls back to `"quick"` with an empty
  ballot) — a closer reading of the task's "if my ballot is in quick mode, prefill quick; if
  detailed, prefill detailed" than assuming a single overall mode, while still degrading to
  exactly that simple behavior in the common case where a rater only ever votes one target
  in one mode.
