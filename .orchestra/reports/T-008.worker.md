# T-008 worker report

## Summary
Built `/g/[groupId]/ajustes`: members list with a permission-aware action menu, invite
creation/listing, guest-player add/claim/assign, and a danger zone (transfer/leave). Every
permission check is centralized in a new pure `lib/permissions.ts`, unit-tested directly
and mirrored 1:1 against the actual SQL in `set_member_role`/`remove_member`/
`create_invite`/`claim_guest_player` (not just the task's prose summary of them). Also
fixed the T-006 "N miembros" regression flagged in the task's step 4.

## Files changed
- `messages/es.ts` — added the full `settings.*` tree (`members`, `invites`, `guests`,
  `danger`), covering every key the task listed.
- `lib/permissions.ts` (new) — `memberActionsFor(myRole, targetRole, isSelf)` plus
  `canInviteAdmin`, `canClaimGuest`, `isGroupAdmin`. Admin↔member and member↔spectator are
  modeled as two independent toggles (an admin is always demoted to `member` first via
  "Quitar admin", never straight to `spectator`, even though the owner's RPC call would
  technically allow that jump) — this keeps the 5 action verbs unambiguous per target role.
  `isSelf` always yields no actions: self role-changes are blocked by the SQL anyway for
  admins (`target_role = 'admin' and caller <> owner` → forbidden even when caller = target),
  and owner/leave/transfer live in the danger zone instead.
- `lib/permissions.test.ts` (new) — all six required cases from the task plus target=owner,
  spectator-facing branches, `canInviteAdmin`, `canClaimGuest`, `isGroupAdmin`.
- `components/settings/member-actions.tsx` (new) — dropdown built from
  `memberActionsFor`, one shared confirm `Dialog` keyed by the pending action.
- `components/settings/member-actions.test.tsx` (new) — renders-nothing cases (self, target
  owner, member-caller, admin-vs-admin), the two non-empty cases from the task, and that a
  destructive action opens the confirm dialog before running.
- `components/settings/invite-form.tsx` (new) — role select (admin option gated by
  `canInviteAdmin`), expiry (1/7/30/never), max uses (blank = unlimited), shows the created
  URL with copy.
- `components/settings/invite-list.tsx` (new) — status derived client-side from
  `revoked_at`/`expires_at`/`uses`/`max_uses` (mirrors `get_invite_preview`'s `valid` logic
  but with the specific reason, since the RPC only returns a boolean); copy via
  `siteUrl()` + code; revoke behind a confirm dialog.
- `components/settings/guest-players.tsx` (new) — admin add-guest form (name + optional
  `POSITIONS`/`es.positions` select); per-guest "Asignar a…" (admin, `assignGuestPlayer`)
  and "Soy yo" (`canClaimGuest`, `claimGuestPlayer`) behind a confirm dialog.
- `components/settings/danger-zone.tsx` (new) — transfer (owner-only, select a non-owner
  member) and leave (disabled + hint for the owner).
- `app/g/[groupId]/ajustes/page.tsx` (new) — loads `group_members`, then a **separate**
  `profiles` query by user id (there is no FK from `group_members` to `profiles` — only to
  `auth.users` — so a PostgREST embed like `group_members.select("profiles(...)")` isn't
  possible; confirmed this against the live schema, see Manual verification), and `players`
  for the group (both the member overlay and the guests bucket, since claimed guests just
  flip `is_guest` to false and fall out of that filter automatically). Renders sections
  conditionally (`Invitaciones` only for admins).
- `app/g/page.tsx`, `app/g/[groupId]/page.tsx` — member-count regression fix: now counts
  `group_members` rows (real members) instead of active `players` rows (which included
  guests). The `[groupId]` home page's avatar *preview* still reads `players` on purpose —
  that's meant to show the visual roster including guests, only the numeric label changed.

## Manual verification
Chrome extension still not connecting (same as T-006/T-007). Instead ran the **exact
Steps sequence from the task's "How to verify"** against the live local stack, using real
magic-link sessions (two, then three, real users via `auth.admin.generateLink` +
`anon.auth.verifyOtp`) and calling the same RPCs the components call:
1. Owner creates a group + member invite (`create_group`, `create_invite`) — matches
   `CreateGroupDialog`/`InviteForm`.
2. Second user joins via the code (`accept_invite`) — matches `JoinButton`.
3. Owner promotes the second user to admin (`set_member_role` → `admin`) — matches
   `MemberActions`'s `makeAdmin`.
4. The new admin creates a **spectator** invite successfully, then an **admin** invite is
   rejected with `PICADO_FORBIDDEN: only the owner can create admin invites` — confirms
   `InviteForm`'s `canInviteAdmin` gate matches the RPC exactly.
5. Owner transfers the group (`transfer_ownership`) — `group_members` afterward shows the
   roles swapped (old owner → admin, new owner → owner) exactly as `DangerZone` assumes.
6. Former owner (now admin) leaves (`leave_group`) — succeeds. The *new* owner then tries
   to leave without transferring — rejected with
   `PICADO_FORBIDDEN: transfer ownership before leaving the group`, confirming the
   `disabled` + `leaveDisabledHint` state on the leave button is correct for whoever
   currently holds `owner`.
7. A second script covered the guest-player paths with three real users (owner, a
   spectator, a member): `add_guest_player` (admin) succeeds; a **spectator** calling
   `claim_guest_player` is rejected (`PICADO_FORBIDDEN: only group members can claim guest
   players`) — confirms `canClaimGuest` correctly excludes spectators; a **member** calling
   it succeeds; `assign_guest_player` (admin, targeting the spectator) succeeds; and
   `remove_member` (admin removing the member) succeeds.
8. Also confirmed directly (`supabase db query --local`, i.e. the actual Postgres schema,
   not just the generated types) that `group_members.user_id` only has an FK to
   `auth.users`, not to `public.profiles` — which is why the settings page fetches
   `profiles` as a second query instead of a PostgREST embed.

  row (`supabase db query --local`, the Postgres superuser connection, since `service_role`

## Known issues / assumptions
- Owner→spectator demotion is only reachable as two clicks ("Quitar admin" then "Pasar a
  espectador"), not one — a deliberate simplification of the action-verb set (see
  `lib/permissions.ts`'s doc comment), not a bug; the RPC allows the one-step jump but the
  UI doesn't expose a button for it.
- `member-actions.tsx`'s confirm `Dialog` opens immediately after a `DropdownMenu` item
  selection (no explicit delay/portal handoff) — this is the standard Radix nested-overlay
  pattern and the component test confirms the dialog renders correctly, but I could not
  verify it visually in a real browser (see above).
