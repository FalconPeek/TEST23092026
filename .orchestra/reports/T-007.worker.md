# T-007 worker report

## Summary
Built the public invite-link landing page and the join flow: format-validate the code,
show a sign-in prompt if not authenticated (no DB call), fetch `get_invite_preview` once
signed in, and either show the invalid state or a join card backed by `acceptInvite`.

## Files changed
- `messages/es.ts` — added `invite.*` (`title`, `joinAs` (fn over `es.roles`), `join`,
  `signInToJoin`, `invalid`, `goHome`).
- `app/invitacion/[code]/page.tsx` (new) — Server Component. Validates `code` against
  `/^[A-Za-z0-9_-]{6,32}$/` before anything else (no DB call for a malformed code either).
  Not signed in → link to `/login?next=/invitacion/<code>`. Signed in → calls
  `get_invite_preview`; **the RPC actually raises `PICADO_INVITE_INVALID` for an unknown
  code** rather than returning zero rows (checked the real migration — the task's Context
  description of "zero rows for an unknown code" doesn't match
  `supabase/migrations/20260923055124_group_rpcs.sql:166-169`), so the page treats
  `error`, a missing row, and `valid: false` all the same way → invalid state. Otherwise
  shows group name, member count, the role-aware `joinAs` line, and `JoinButton`.
- `components/invite/join-button.tsx` (new) — client, calls `acceptInvite({ code })`,
  `router.replace` to the joined group + `toast.success` on success, `toast.error` with
  the already-mapped message on failure.
- `components/invite/join-button.test.tsx` (new) — mocks `next/navigation`, `sonner`,
  `@/lib/actions/groups`; covers the success-navigates and error-toasts paths.

## Known issues / assumptions
- Treated "invite not found" (RPC error) and "invite found but invalid" (`valid: false`
  row) identically as the invalid state, per the acceptance criteria ("never an error
  page") — confirmed this is in fact how `get_invite_preview` behaves for an unknown code,
  not what the task's Context section described.
- No distinction is shown between "expired", "revoked", and "usage limit reached" on the
  invite *preview* screen (`get_invite_preview` only returns a boolean `valid`); the
  specific reason only surfaces if the user actually clicks join and `acceptInvite`/
  `mapDbError` returns the precise mapped message via toast. That matches the RPC's own
  shape — `get_invite_preview` doesn't expose why an invite is invalid, only whether it is.
